# 对话 → Spec（Android 版）

把当前对话上下文与代码库理解综合成一份 spec。**不要采访用户**，只综合已知信息。

## 流程

1. 探索代码库理解现状（如果还没做）。项目存在 `.qoder/context/`、CONTEXT.md 或 docs/ 业务文档时先读，通篇使用项目领域词汇；尊重已有 ADR，不重翻旧案。

2. 草拟测试**接缝（seam）**：优先复用现有接缝而非新开。Android 项目的典型接缝：
   - 纯函数/工具类（校验/格式化/计算）
   - Repository / DataSource（参数组装与响应解析）
   - UseCase / Interactor、ViewModel（状态产出）
   - 能用高层接缝就不用低层的；全代码库接缝越少越好，理想值是一。

   与用户确认这些接缝符合预期。

3. 按下方模板写 spec，保存到 `docs/specs/<feature-name>.md`（目录不存在则创建）。保存后告知用户文件路径。

<spec-template>

## 问题陈述

从用户视角描述要解决的问题。

## 方案

从用户视角描述解决方案。

## 用户故事

足够详尽的编号列表，格式：`作为 <角色>，我希望 <功能>，以便 <收益>`。覆盖功能的各个方面。

## 实现决策

已确定的实现决策列表，可包括：
- 将新建/修改的模块与归属（feature 模块划分、模块间依赖方向）
- 模块对外接口的变化（方法签名层面，不写代码）
- 架构决策与理由（数据流走向：Repository/UseCase/ViewModel/UI）
- 数据模型变化（含 Room Entity/数据库迁移）
- 与服务端的接口约定
- 路由与跳转关系

不要写具体文件路径与代码片段（很快会过时）。
例外：若某个决策用代码结构表达比文字更精确（状态机、枚举定义、数据形状），可内联最精华的片段，并注明"仅为决策示意"。

## Android 专项决策

- **兼容范围**：minSdk / targetSdk / compileSdk；受影响系统版本的适配点；ABI 范围
- **权限清单**：AndroidManifest 声明项 + 运行时申请时机与拒绝降级；厂商 ROM 的特殊处理（如通知权限/自启动引导）
- **多环境/多渠道**：host 与开关在各环境取值；渠道包差异（如有）
- **降级与灰度**：功能开关位置、灰度范围、低版本系统表现
- **性能预算**：启动/页面/帧率指标与降级策略

## 测试决策

- 好测试的标准（只测外部行为，不测实现细节）
- 将测试哪些模块、在哪些接缝测
- 代码库中可参考的既有测试先例

## 明确不做（Out of Scope）

本 spec 明确排除的内容。

## 备注

其他需要记录的信息。
