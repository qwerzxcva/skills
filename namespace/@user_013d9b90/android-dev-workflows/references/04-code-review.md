# 双轴代码评审（Android 版）

对用户提供的固定点与 HEAD 之间的 diff 做两轴评审：

- **规范轴（Standards）**：代码是否符合本仓库成文的编码规范 + Android 崩溃/质量基线 + Fowler 坏味道基线。
- **Spec 轴**：代码是否忠实实现了需求/spec。

两轴**独立评审**（可用并行子代理防止上下文互相污染），本模块汇总两方结论。

## 流程

### 1. 固定基准点

用户说的固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。没说就问。

一次性确定 diff 命令：`git diff <fixed-point>...HEAD`（三点，对 merge-base 比较）。同时记录提交列表 `git log <fixed-point>..HEAD --oneline`。

继续之前确认基准点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏引用或空 diff 必须在这里失败，而不是带进两个并行评审。

### 2. 确定 Spec 来源

按此优先级寻找：

1. 用户指定的 spec 文件路径。
2. `docs/specs/` 下与分支名/功能匹配的 spec。
3. 提交信息中的 issue 引用。
4. 都没有：问用户。用户说没有 → Spec 轴跳过，报告中注明"无 spec 可对照"。
5. 兜底：若以上皆无但对话上下文中需求明确，以对话需求为准并注明来源。

### 3. 确定规范来源

仓库中任何成文的"代码该怎么写"文档，自动探测（存在即用，可多份叠加）：

- `.qoder/rules/*.md`（Qoder 规则体系）、`CODING_STANDARDS.md` / `CONTRIBUTING.md` / `AGENTS.md` / `CLAUDE.md`
- `.github/instructions/`、`.clinerules`、`.cursor/rules/`
- lint/ktlint/detekt 配置（已强制的事项不再重复报告）

在仓库文档之上，规范轴始终叠加两条基线：

**Android 崩溃/质量基线（硬性，违反即 CRITICAL）：**

- **Context 泄漏**：静态字段/单例/内部类持有 Activity/Fragment/View；长生命周期对象存 UI 引用
- **主线程违规**：主线程做网络/磁盘 IO/大计算（NetworkOnMainThread、ANR 风险）；数据库/文件操作未切后台线程
- **协程/线程泄漏**：`GlobalScope.launch` 滥用；协程未绑定 lifecycleScope/viewModelScope；线程池任务未取消
- **生命周期**：异步回调到达时页面已销毁仍操作 UI；未处理配置变化重建导致状态丢失/重复请求
- `!!` 非空断言、裸 `as` 强转、对可空字段先判后用的竞态（`if (x != null) x!!.`）
- 列表/数组越界（服务端数据条数与本地不一致时）
- 资源硬编码：颜色/尺寸/文案写死在代码里（不走 res）、魔法值（未注释的状态码/数字）
- `Log.d/e` 调试残留、被注释的大段旧代码

**Fowler 坏味道基线**（启发式，永远是判断题）：神秘命名 / 重复代码 / 依恋情结 / 数据泥团 / 基本类型偏执 / 重复 switch / 霰弹式修改 / 发散式变化 / 投机性泛化 / 消息链 / 中间人 / 被拒绝的遗赠。

基线规则：**仓库成文规范优先**（仓库明确认可的做法，即使基线会标记，也压制该告警）；工具已强制的事项（lint/detekt 已覆盖的）跳过。

### 4. 并行评审两轴

**规范轴**输入：完整 diff 命令与提交列表；第 3 步找到的规范文件清单 + Android 基线 + Fowler 基线全文。要求：逐文件/hunk 报告 (a) 违反成文规范的位置：引用规范（文件+条款）；(b) 发现的基线问题：命名并引用 hunk。区分硬性违规与判断题。400 字以内。

**Spec 轴**输入：diff 命令与提交列表；spec 内容。要求：报告 (a) spec 要求但缺失/部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似实现但实现有误的需求。每条引用 spec 原文。400 字以内。

无 spec 时跳过 Spec 轴，在最终报告中注明。

### 5. 汇总

在 `## 规范轴` 与 `## Spec 轴` 两个标题下分别呈现两方报告（原文或轻度清理）。**不要合并、不要跨轴重排**——两轴故意分离（见下）。

最后一行总结：每轴发现数 + 各轴内最严重的问题（如有）。不要在两轴间选"总冠军"——那正是分离要防止的重排。

## 为什么要两轴

一次改动可能过一轴挂另一轴：

- 每条规范都符合但做错了事 → **规范过，Spec 挂**。
- 完全按需求实现但破坏了项目约定 → **Spec 过，规范挂**。

分开报告，防止一轴掩盖另一轴。
