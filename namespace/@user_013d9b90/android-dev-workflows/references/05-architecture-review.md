# 架构体检（Android 版）

暴露架构摩擦，提出**加深机会（deepening）**：把浅模块（接口几乎和实现一样复杂）变成深模块（小接口背后承载大量行为）。目标是可测试性与 AI 可导航性。

项目存在 `.qoder/context/`、CONTEXT.md 或 docs/ 业务文档时先读；报告中使用项目领域语言，不用代码符号名说话。

## 流程

### 1. 探索

**先圈范围再扫描（YAGNI）**：加深的收益是让未来的改动更容易，所以权重压在**近期频繁变动**的区域：

- 用户指定了方向（模块/子系统/痛点）→ 直接用，跳过下面的推断。
- 否则回看一段提交历史（`git log --oneline`）找热点：反复出现的文件与区域优先；改动分散无热点再撒大网。

然后派子代理走读代码库，不用死板规则，有机探索并记录摩擦点。**Android 典型信号**：

- **巨型 Activity/Fragment**：单类超约 800 行；UI/数据组装/网络/业务判断全塞一起；`onCreate` 过百行
- **Massive Application**：启动初始化/全局单例/工具静态方法全堆 Application 子类
- **UI 层直发请求**：Activity/Fragment/Compose 里直接 Retrofit/OkHttp 调用，绕过 Repository
- **绕过路由/导航**：跨模块直接 startActivity 引用对方页面类，模块边界名存实亡
- **跨模块直接引用内部实现**：绕过公开接口/门面 import 对方 internal 类；Gradle 模块循环依赖
- **全局状态垃圾桶**：什么都塞进 Application 级单例/静态字段，且感知 UI 层
- **广播/EventBus 乱飞**：字符串 action/事件名接力传递状态，无法静态追踪
- **数据模型染指视图**：纯 Model/data class import Android Framework 或 UI 组件，无法 JVM 单测
- **浅模块**：接口和实现一样复杂；为可测性拆出的工具类，真正的 bug 藏在调用方式里（无局部性）
- **ViewModel 膨胀成胖 VC**：ViewModel 又做业务又做数据加工还感知 Context
- 哪些区域没有测试，或无法通过现有接口测试？

对疑似浅模块应用**删除测试**：删掉它，复杂度是集中了还是只是搬家了？"集中了"才是要找的信号。

### 2. 候选以 HTML 报告呈现

写自包含 HTML 到系统临时目录（`$TMPDIR`，回退 `/tmp`），文件名 `architecture-review-<timestamp>.html`，写完 `open` 打开并告知绝对路径。不要落进仓库。

报告用 Tailwind CDN 排版；关系图用 Mermaid CDN（模块依赖图/调用时序），编辑性图示（体量图、剖面图）用手写 div/SVG。每个候选给**前后对比可视化**。要视觉化。

每个候选项一张卡片：

- **涉及文件**：哪些类/模块
- **问题**：当前架构为何造成摩擦
- **方案**：白话描述怎么改
- **收益**：用局部性与杠杆解释；测试将如何变好
- **前后对比图**：并排，手绘，体现"浅"与"加深"
- **推荐强度徽章**：`Strong` / `Worth exploring` / `Speculative`

报告末尾给 **Top 推荐**：先动哪个、为什么。

**用词用项目领域语言**：如果业务文档里叫"入库模块"，就说"入库模块"，不说"StockInHandler"。

若候选与已有 ADR 冲突：仅当摩擦真实到值得重开 ADR 时才提出，并在卡片上明确标注（如警告条："与 ADR-0007 冲突，但值得重开，因为……"）。

此阶段**不设计接口**。文件写好后问用户："想深入哪一个？"

### 3. 拷问循环

用户选定候选后，调用 `references/00-requirement-grilling.md` 走决策树：约束、依赖、加深后模块的形状、什么藏在接缝后面、哪些测试存活。

决策固化时的副作用就地处理：

- 给加深模块起了新概念名？→ 补进项目领域词汇文档（`.qoder/context/` 或 CONTEXT.md / docs/），文件不存在就惰性创建。
- 用户以有分量的理由否决候选？→ 提议记录为 ADR："要不要记成 ADR，免得以后架构体检重复推荐它？"仅当理由对未来探索者有用才提议；一时性理由（"现在不值得"）跳过。
