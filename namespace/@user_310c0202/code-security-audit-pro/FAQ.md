# 常见问题（FAQ）

## 一、功能能力

**Q1：代码安全审计的准确率有多高？会不会漏报或误报？**

A：本工具覆盖OWASP Top 10常见漏洞模式（SQL注入、XSS、命令注入等典型场景），但**不提供经实测验证的检出率/误报率数值**。注入类等模式较典型的风险识别相对可靠；业务逻辑、权限绕过等需要理解业务上下文的漏洞，在仅给孤立代码片段时较易漏报。误报主要集中在：被误判为有风险的安全输入验证、框架内置安全机制未被识别、特定业务场景下的可控参数。**实际检出效果取决于代码质量与上下文完整度，所有结论均需人工复核后再确认，本工具不替代专业渗透测试。**

**Q2：支持哪些编程语言？覆盖率如何？**

A：支持多种主流编程语言：Python、Java、JavaScript、TypeScript、Go、Rust、C/C++、PHP、Ruby、Swift、Kotlin、Solidity。Web开发类语言（Python/Java/JS-TS/PHP）与Django、Flask、FastAPI、Spring、Express等主流框架的检测经验更成熟；系统编程、移动端、智能合约等语言相对依赖通用规则。**以上为相对成熟度的定性说明，不代表实测覆盖率；具体效果仍以代码上下文与人工复核为准。**

**Q3：一次能审计多少代码？有限制吗？**

A：建议单次审计代码量控制在1000行以内效果最佳，这一范围能达到最优的检测深度和准确率。超过1000行的代码会自动分段审计，但检测粒度会适当放宽，可能影响准确率。对于大型项目建议按文件或按功能模块分批审计。如果是完整项目，可以先提供核心模块、入口文件、认证授权相关代码进行重点审计。

**Q4：跟传统SAST工具（如SonarQube、Semgrep）有什么区别？**

A：主要区别在于：① 检测深度不同——传统SAST基于规则匹配，能精确但死板，复杂逻辑漏洞检测能力弱；本工具基于语义理解，能检测更复杂的逻辑漏洞，但可能有误报。② 修复建议质量不同——传统工具只报漏洞位置和CWE编号；本工具提供完整的修复代码示例和原理解释。③ 使用门槛不同——传统工具需要配置规则、集成到CI/CD；本工具直接粘贴代码即可用。④ 互补关系——两者不是替代关系，而是互补。建议日常快速审计用本工具，流水线集成用传统SAST。

**Q5：能检测业务逻辑漏洞吗？比如越权、竞态条件？**

A：可以检测部分业务逻辑漏洞，但需要足够的代码上下文和业务背景信息。如果只给一个孤立的函数片段，很难判断是否存在越权；但如果提供完整的接口代码+路由配置+鉴权逻辑，就能更可靠地提示水平越权、垂直越权、IDOR等问题。竞态条件、批量攻击、逻辑绕过这类漏洞最依赖对完整业务流程和并发场景的理解，通常只能作为"可疑"提示而非确定结论。建议审计业务逻辑漏洞时，尽量提供完整的业务背景和相关代码。

**Q6：审计结果和修复方案可以直接用在生产环境吗？**

A：不建议直接照搬。原因有三点：① 审计结果可能存在误报，需要人工验证确认；② 修复方案是通用安全最佳实践，需要结合你的具体业务逻辑和技术栈调整；③ 直接修改代码可能引入新的bug或破坏现有功能。正确的做法是：对每个高危漏洞先确认是否为真实漏洞，然后根据项目实际情况调整修复方案，修改后充分测试再上线。

**Q7：能检测0day漏洞吗？还是只能检测已知漏洞模式？**

A：主要检测已知的漏洞模式和常见的安全弱点（CWE/CVE模式）。对于全新的0day漏洞——即从未公开过的漏洞类型——无法保证能检测出来。但工具具备一定的异常模式识别能力，对于"看起来不安全的代码模式"（如未验证的用户输入直接进入危险函数、不规范的认证实现等）会标记为可疑。但0day漏洞的发现仍然需要专业安全研究员的人工分析和漏洞挖掘能力。

**Q8：修复代码示例可靠吗？会不会有问题？**

A：修复代码基于安全编码最佳实践生成，方向是正确的，但不能保证100%适用于你的项目。常见的问题包括：修复代码可能与你的代码风格不一致、可能没有考虑你的业务特殊逻辑、可能依赖你项目中没有的库或工具。建议把修复方案作为参考方向，根据项目实际情况进行调整，并经过测试验证后再合入代码库。对于关键模块的安全修复，建议安排Code Review。

## 二、使用场景

**Q9：适用于什么场景？不适用于什么场景？**

A：
- ✅ 适用场景：代码提交前快速自查、学习安全编码知识、第三方代码引入前评估、面试/笔试题安全评估、Code Review辅助、安全培训教学演示。
- ❌ 不适用场景：替代专业渗透测试（需要人工渗透测试工程师做全面安全评估）、100%自动化的安全门禁（有误报漏报，不能完全依赖）、二进制文件/编译后代码审计（需要源代码）、实时线上漏洞自动修复（修复方案需人工验证）、合规审计出报告（需要有资质的安全机构出具）。

## 三、反模式警告

**❌ 反模式1：把审计结果当作金科玉律，全部当真**

- **错误做法**：工具报什么漏洞就信什么，所有标"严重"的全部紧急修复，没有任何质疑。
- **原因**：SAST工具普遍存在误报，AI审计也不例外。尤其是业务逻辑类、配置类的漏洞误报率较高，直接全信会浪费大量时间修复假阳性。
- **正确做法**：先过一遍漏洞列表，结合业务场景判断真实性。高危漏洞优先确认，中低危漏洞批量评估，误报直接忽略。建立自己的误报案例库，逐步优化判断效率。

**❌ 反模式2：只贴几行代码片段就想做完整审计**

- **错误做法**：只贴一个函数里的几行代码，指望工具能发现所有安全问题。
- **原因**：安全漏洞往往是上下文相关的——输入从哪里来、有没有经过验证、函数调用链是什么，这些都需要完整的上下文才能准确判断。只看片段容易误报或漏报。
- **正确做法**：提供尽可能完整的代码上下文——包括输入来源、中间处理、输出去向。如果是接口审计，至少提供路由层+控制层+服务层的完整调用链。框架使用说明也能帮助提升准确率。

**❌ 反模式3：用代码审计工具来检测提示注入等AI安全问题**

- **错误做法**：把系统提示词贴进代码审计，问"这个提示词安全吗"。
- **原因**：本工具是代码安全审计，专注于代码层面的安全漏洞。Prompt安全、提示注入检测属于AI安全范畴，需要专门的提示注入检测工具。
- **正确做法**：代码安全问题用代码审计工具，Prompt安全问题用专门的提示注入检测工具，两者是不同领域的安全工具。

**❌ 反模式4：审计完不改，只是走个过场**

- **错误做法**：每次提交前跑一遍审计，看完报告就关掉，漏洞一个不修。
- **原因**：安全审计的价值在于修复和改进，而不是"我审计过了"的心理安慰。只审计不修复等于没审计。
- **正确做法**：建立漏洞修复流程——高危漏洞立即修复，中危漏洞排期修复，低危漏洞记录跟踪。每次迭代回顾漏洞修复率，持续提升代码安全水平。

**❌ 反模式5：修复后不测试，直接上线**

- **错误做法**：照着修复代码复制粘贴进去，不跑测试直接合入主分支。
- **原因**：安全修复可能引入新的bug——破坏原有功能、引入性能问题、产生新的安全问题。安全修复代码也是代码，也需要测试验证。
- **正确做法**：每个安全修复都要经过：功能测试+安全测试双重验证。功能测试确保修复不破坏原有功能，安全测试确保漏洞确实被修复了。重要修复建议增加回归测试。

**❌ 反模式6：只审计一次就完事，不做持续安全**

- **错误做法**：项目上线前审计一次，之后再也不做安全检查了。
- **原因**：安全是持续的过程，不是一次性的活动。新代码可能引入新漏洞，依赖库的漏洞也在不断被发现。一次审计只能保证审计时刻的状态。
- **正确做法**：建立持续安全机制——代码提交前自查、定期全面审计、依赖库漏洞监控、新漏洞预警。安全是日常工作，不是项目节点。

**❌ 反模式7：用AI生成的代码不审计，认为AI写的就是安全的**

- **错误做法**："这是AI生成的代码，应该没问题吧，直接用。"
- **原因**：AI生成代码的代码可能包含训练数据中的常见漏洞模式，而且AI本身不具备安全判断能力。实际上，AI生成代码的漏洞率并不比人写的低不了多少。
- **正确做法**：不管是人写的还是AI生成的代码，只要进入生产环境，都要做安全审计。AI生成的代码尤其要仔细审查，因为你可能不熟悉其中的逻辑，出了问题更难排查。

## 四、边界与限制

### 能做什么（核心能力）

1. **50+类漏洞检测**：覆盖OWASP Top 10、CWE Top 25等主流安全弱点，包括注入类、认证授权、数据安全、输入验证、配置安全等
2. **12种编程语言支持**：Python、Java、JavaScript/TypeScript、Go、Rust、C/C++、PHP、Ruby、Swift、Kotlin、Solidity深度检测
3. **可落地修复方案**：每个漏洞都有原理分析、攻击场景、修复代码示例和参考链接，不只是报漏洞编号
4. **风险分级评估**：按严重/高危/中危/低危/信息五级分类，帮助优先处理修复优先级
5. **安全编码教育**：不仅找漏洞，还讲原理和最佳实践，帮助开发者提升安全意识

### 不能做什么（明确局限性）

1. **不能100%准确检测所有漏洞**：复杂业务逻辑漏洞、需要深度上下文理解的漏洞、非常见模式的漏洞可能漏报；同时存在一定误报率
2. **不能检测运行时漏洞**：静态分析只能看代码本身，无法检测运行时才出现的问题（如并发竞态条件的实际触发、环境配置问题等）
3. **不能审计编译后的二进制文件**：需要源代码才能审计，不支持反编译或二进制分析
4. **不能替代专业渗透测试**：工具审计是辅助手段，不能替代人工渗透测试和专业安全评估
5. **不能保证修复代码100%可用**：修复方案是通用示例，需要结合项目实际调整，不能保证直接复制就能用
6. **不支持完整项目级别的全量扫描**：单次处理能力有限，大型项目需要分批审计，无法像专业SAST工具那样做全项目扫描

### 检出效果定性说明（非实测指标）

- 本工具**未提供经 OWASP Benchmark / WebGoat / DVWA 等测试集量化评测得出的检出率/误报率数值**，相关百分比已从文档中移除。
- 各类风险的可靠度为定性判断：注入类等模式较典型，业务逻辑类最依赖上下文。
- 实际效果受代码完整性、上下文充分性、框架类型等因素影响；提供的代码越完整、上下文越清晰，判断越可靠。
- 所有"严重/高危"结论均应人工确认真实性后再修复。

### 已知盲点与薄弱场景

- **复杂业务逻辑漏洞**：如水平越权、业务流程绕过、支付逻辑漏洞等需要深度业务理解的漏洞
- **并发/竞态条件漏洞**：静态分析难以准确判断并发场景下的时序问题
- **加密实现缺陷**：复杂的密码学实现错误检测能力有限
- **微服务架构下的跨服务漏洞**：只看单个服务代码难以发现服务间调用的安全问题
- **配置文件和环境变量中的敏感信息**：只审计代码本身，不扫描配置文件、环境变量等非代码内容
- **0day漏洞和新型攻击手法**：基于已知模式检测，对全新漏洞类型检测能力有限
