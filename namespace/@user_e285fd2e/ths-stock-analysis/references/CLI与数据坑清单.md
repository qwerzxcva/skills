### 获取数据类坑（优先级最高）

1. **`special hot-stock-history` 的 `--date` 参数无效**：实测查 2026-01-05 与 2026-08-21 返回完全相同（永远=最近交易日热榜）。**历史日热榜不可回溯** → 标 [MISSING]，用龙虎榜净买 TOP3 替代为"资金关注焦点"。（2026-08-23 实测：宇树科技未上市却在 01-05 热榜暴露）
2. **`special limit-up-ladder`（连板梯）只返回最近 30 个交易日** → 历史日的连板梯队从涨停池 `continue_day_cnt` 字段重建（分组统计各连板数家数）。
3. **`special anomaly-list`（异动列表）为当日实时能力**，历史日不可查 → 标 [MISSING]。
4. **热榜历史接口的 `heat`（热度值）字段为 None** → 只展示排名，页脚注明。
5. **龙虎榜接口无买卖席位明细**（仅汇总净额+机构/游资净额）→ 知名游资席位需 WebSearch 公开披露补充，**页面显式标注"WebSearch 公开披露"**（数据来源铁律）；机构分析用 `--board-type org` 版（有 org_net_value/org_buy_num/org_sell_num）。
6. **涨停池默认查当天**（非交易日返回空）→ 必须指定 `--date-ms <当日0点毫秒>`；`limit_up_reason` 含板块标签（板块热度数据源）、`continue_day_cnt` 含连板数。
7. **指数涨跌幅**：`index history` 拉包含目标日与前收的窗口，用目标日收盘 vs 前一交易日收盘计算（接口对远古窗口可能无数据，需从更早起点拉取）。
8. **龙虎榜数据坑**：`change` 为小数比例（0.10=+10%）；同股多次上榜需按 ticker 合并；`hot_money_net_value` 部分条目缺失用 `.get()`；Hero KPI 正负号必须 `{:+.2f}` 格式化（禁止硬编码"+"→ 负值会出现"+-"）；模板 insight 为当日叙事，换日期必须逐一替换硬编码。
9. **涨跌家数**：本地库 `db query` 用 `close > open` 统计（raw_kline_daily 列名为 `close/open/date`，无 close_price 列不会触发误判）；本地库无指数表。
10. **历史K双结构**：本地结构 `data`(list)+`date`/`close`；远端/ETF 结构 `data.item[]`+`date_ms`/`close_price`——解析必须兼容两种（个股用本地前复权，ETF 用 fund.history 远端）。
11. **数据交叉验证（方法论）**：接口返回"看起来合理"的数据时，用业务常识校验——次新股上市日期（名字带 C/-W 后缀=刚上市，历史日期不可能出现）、XD 除息标记（只出现在除息日）、与涨停池/龙虎榜名单交叉比对。发现可疑数据宁可标 [MISSING]。
12. **估值数据坑（能力 #4）**：①`valuation` 仅 A 股（港股/美股报错 CLI_BAD_ARGUMENT）且只有 snapshot——**无历史估值/行业估值接口，历史分位必须回溯法自建**（历史PE_i=当前PE_TTM×前复权价比例）②market snapshot 无市值字段（回溯法不需要股本）③**SVG fill 不支持 CSS linear-gradient 字符串**（会回退黑色）→ 一律纯色④**盈利高增股回溯法低估历史 PE**（按当前 TTM 净利回溯，净利翻倍+标的口径，页脚/风险注明）⑤行业对比公司必须按标的主营选同行（电网设备/黄金铜业等）。⑥**Hero KPI 标签曾硬编码「5年92%分位」（紫金矿业旧版残留）→ 已改为 __PERC_KPI__ 占位符由 PERC['p5']['pe'] 动态生成**（2026-08-24 汾酒验证暴露：汾酒实际 3% 分位却显示 92%）——**报告模板禁止把数值硬编码进 TPL，一律占位符+数据区驱动，生成后 grep 旧数值残留**
13. **财务预测器坑（能力 #3）**：①`financials income` 返回**倒序**（最新在前）且**无 yoy 字段需自算** ②最新报告期判断：先用 quarterly 确认（亨通最新=2026Q1 而非中报）③一致预期可能被激进机构拉高（亨通 2026E 79 亿 vs 分机构 40-50 亿）→ 中性取券商区间中枢并提示 ④三情景预测必须标 [MODEL]/[ASSUMED]（模型输出非公司指引），券商数据页脚标注来源 ⑤敏感性矩阵用"营收×净利率"而非单变量，表达预测区间宽度。 ⑦**03/04 区块 insight/hint 曾硬编码亨通文案**（'中性 45 亿/AI光纤+海缆'残留）→ 已改为 __SCEN_INSIGHT__/__DRIVER_HINT__ 占位符，新增变量用插入（模板无此行，replace 会静默失败）⑧**假设表第一列 sum-tag 标签窄列宽下换行成两行 → 已加 white-space:nowrap**（2026-08-24 汾酒验证暴露）——**所有模板区块级 hint/insight 必须占位符化，新变量插入而非替换，生成后 grep 旧标的名/旧行业词残留**。⑥**模板字段类型强约束（2026-08-24 汾酒验证）**：SCENARIOS 键必须是中文「乐观/中性/悲观」且含 desc 字段；BROKERS 值为数字（非字符串）；DRIVERS 为 3 元组（icon, 标题, 描述）——填错类型渲染时 ValueError，先看模板渲染函数再填数据。
14. **业绩前瞻日历坑（能力 #5）**：①**hithink 无业绩披露日历接口**（`market calendar` 仅交易日且返回一年窗口，窗口在年内可核对、超出需按 A 股规则推算）→ 披露安排/业绩预告必须 WebSearch 交易所预约+新闻报道，**页脚显式标注来源** ②披露量分布为新闻口径（各源有差异，取主源）③盲盒清单要标注统计时点（如"8-14 时未披露口径"）并提示可能已提前披露 ④披露日为预约制可调整，风险区注明 ⑤业绩预告为区间（上限/下限），实际披露可能落低位。
15. **板块轮动坑（能力 #7）**：①板块指数用 `index catalog --tag industry`（881xxx.TI 一级行业 90+，另有一批 884xxx 细分行业）②**板块指数历史含 turnover（成交额）**——量比（5日均成交/20日均成交）与动量可同源计算 ③行业指数代码带 .TI 后缀（同花顺专属），与指数快照 .SH/.SZ 不同 ④轮动表内"20日"数值列与"20日动量"进度条列为同一数据双列（非错误）→ 避免重复展示，进度条列与排名区二选一 ⑤`__VERDICT__` 等占位符在模板中只能替换一次（曾放 vbadge+粗体两处导致判定词重复）。
16. **穿透分析坑（能力 #9）**：①**hithink 无"个股被哪些基金持有"接口** → 反向穿透必须 WebSearch 公开披露（新浪基金持股页/巨丰/东吴等），页脚显式标注来源与口径（渤海=主动权益基金数、巨丰=全口径、东吴=占总市值比例）②`fund industry-allocation` 可能报 FUYAO_5003（status 9999 retryable）→ 行业分布用持仓股主营归类或标 [MISSING] ③持仓报告期（2026Q2 季报）与持有人报告期（2025-12-31 年报）不同需分别标注 ④**闭环验证**：正向持仓股应能在反向持有基金表中找到该 ETF 本身（换标的必查）⑤**抱团图双列布局**：右列起始 x2 固定并与图例对齐、左列条宽受限于 x2（值文本不越界）、右列条宽按可用宽度（曾公式负值→全 4px 条+重叠）⑥**占位符唯一性**：title 用 __DATE_SHOW__（曾 {DATE} 显示字面量）、闭环判断用 CFG["etf_code"] 动态取（曾硬编码 512480）⑦模板全参数化：KPI/档案/持有人/insight/解读/风险行必须在数据区，禁止 TPL 写死当日叙事 ⑧**layer_svg 颜色表只支持 4 层，LAYERS 超 4 层会 IndexError → 已修复为 `colors[i % len(colors)]` 取模循环**（2026-08-24 协鑫集成 5 层验证暴露）⑨**SHAREHOLDERS 占比列必须为数字**（模板 `{pct:.2f}%` 格式化，传 "8.89%" 字符串会 ValueError）。 ⑩**layer_svg 固定高度 H=260 是按 4 层设计，LAYERS 超 4 层（如 5 层）时底部行与图注超出 viewBox 被裁剪显示不全 → 已改为动态高度 `H = pad_t + len(LAYERS)*(row_h+gap) - gap + 30`**（2026-08-24 协鑫 5 层验证暴露）。
17. **组合风险坑（能力 #10）**：①**不同量纲资产不能直接加权**：ETF 价格（0.87）与指数点位（2500）混合加权会淹没收益 → 组合净值必须先各自归一化到 1 再按权重相加 ②`fund history` 为远端结构 `data.item[]`+`date_ms`/`close_price`，与本地 K 线结构不同（**个股组合改用本地 DuckDB v_daily_qfq 前复权日K**）③年化收益/波动按 252 交易日换算、相关系数基于日收益率（窗口对齐取交集）④最大回撤需记录峰值日~谷底日区间 ⑤分散模拟标 [MODEL]（历史窗口回测，红利在股灾时也大跌）⑥相关性着色约定：>0.7 红 / 0.4-0.7 橙 / 0-0.4 蓝 / <0 绿 ⑦kv_rows 渲染函数需兼容字符串列表（风险行）与 (k,v) 元组两种输入（DIAG 必须 2 元组）⑧**DIVERSIFY 行 ret/vol/dd 可为 None（定性建议行）→ div_rows 已加 None 保护显示 "--"**（曾 ret=None 崩溃）⑨**相关系数方差公式必须 `(sum/len)**0.5`**（曾写 sum/len**0.5 因运算符优先级导致方差算错、相关系数全部失真——2026-08-24 协鑫+汾酒验证时暴露）⑩**个股组合验证**：协鑫(+0.2%)+汾酒(-37.7%) 相关 0.089、组合 -19.2%——"分散波动 ≠ 分散行业下行"，文案必须基于真实数据（汾酒一年深跌 -37.7% 是白酒行业回调，不是个股偶发）。

## 2026-09-10 追加（36-40）· 9 大短线策略回测

39. **连续 N 根阳线不能用累计 SUM 代替（真实连续长度的正确算法）**（能力 #1 SQL，2026-09-10 实测，隐蔽性高）：`SUM(CASE WHEN close>open THEN 1 ELSE 0 END) OVER (PARTITION BY thscode ORDER BY date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` 得到的是**全历史累计收阳数（实测高达 168）**，不是"截至当日的连续长度"→ 使 `cnt_up>=3` 类条件**恒不成立**、`first_red_pullback` 策略 0 笔交易（**且不报错、静默返回 0 笔，极易漏检**）。正确算法=**「收阴日分组 + 组内行号」**：`ROW_NUMBER() OVER (PARTITION BY thscode, grp ORDER BY date)`，其中 `grp = SUM(CASE WHEN close>open THEN 0 ELSE 1 END) OVER (PARTITION BY thscode ORDER BY date)`，并对阴线日置 0。**同类陷阱**：判断"昨日是否长阳"必须取 `LAG(cnt_up)`（`prev_cnt_up`）——阴线当日 `cnt_up` 恒为 0，用当日值判断"前有长阳"永远失败。**排查经验：策略返回 0 笔时先查该信号依赖的字段分布（`GROUP BY 字段` 看取值范围），而不是先怀疑数据。**

### 方法论补记（不是 CLI 坑，但同样重要）
- **「事后归因」不等于「可执行规则」**：复盘时若按"结果"给标的贴标签（如"左侧标的""退潮链"），分组差异会非常好看；但换成**事前可算的特征**（动量/涨跌/均线位置/距高点距离）再分组，往往全部失效——2026-09-16 首次复盘实测就是如此（20 日动量甚至**反向**）。**判据：一个分组如果只在事后成立、换成事前可算特征就消失，它就不是规则。**

## 66. `ensure_data.py --check` 的「已最新」不含当天（2026-09-21 实测）

**现象**：2026-09-21（周一）晚间 23:45 跑 `ensure_data.py --check` → 输出「✅ 数据已最新：本地 2026-09-18 == 最近交易日 2026-09-18，可直接开工」，
但当天（09-21）的日线包其实**已经发布**，本地库当时并没有 09-21 的数据。

**原因**：`ensure_data.py` 的判据是「**最新完整交易日 = 日历中 < 今天 的最大日期**」（保守口径，设计如此），
所以它**在任何时刻都不会把"今天"当作同步目标**——即使当天收盘后包已发布、跑完 sync 后本地库确实到 09-21，
`--check` 仍然只会说"已最新（09-18）"。

**正确做法**：当天收盘后要产出**当天**的报告 → **直接跑 `data sync`**（不要依赖 `--check` 的结论），
以返回的 `release_id`（形如 `YYYYMMDD/a_share_daily_k_1d_none_10d_YYYYMMDD.parquet`）与本地库 `SELECT max(date) FROM v_daily_qfq` 为判据。
实测 2026-09-21 23:47 跑 sync：`decision=INCREMENTAL`、`release_id=20260921/...`、耗时 147.9s，随后本地库到 2026-09-21。

**注意**：`data sync` 耗时可能 2~3 分钟甚至更久 → 放到后台跑并把输出**重定向到文件**（不要接管道），
同时并行做不依赖本地库的 API 拉取（涨停池 / 指数历史），同步完成后再导出 parquet、跑形态扫描。

## 68. CLI 单次调用有 ~1.2s 固定开销 → 独立调用必须并行（2026-09-21 实测）

**事实**：单次 `hithink-finance` 调用耗时 **1.1~1.6s**，与查询体量几乎无关（node 启动 ~1s + 网络握手）。因此**耗时 ≈ 调用次数 × 1.3s**。

**实测（2026-09-21，本机）**：
| 步骤 | 串行 | 并行（workers=8） | 加速 |
|---|---|---|---|
| 27 条板块指数历史 | 41.9s | 12.4s | 3.4× |
| 5 个当日池/龙虎榜 | 6.5s | 5.8s | 1.1× |
| 估值 1 次 + 10 只财务指标 | 14s | 7.1s | 2.0× |
| **三项合计** | **≈62s** | **26.9s** | **2.3×** |

**规范**：**≥3 个彼此独立的 CLI 调用一律用 `ths_cli.run_many(arg_lists, workers=8)`**（唯一实现，按输入顺序返回、单项失败不抛异常）。
`workers` 取 8：实测 4→13.3s、8→11.2s、12→11.2s（再往上无收益，node 启动争抢 CPU）。

**注意**：
- `index history` **只接受单个 `--thscode`**（无批量参数）→ 27 条必须 27 次调用，只能靠并行；
  `index snapshot` / `valuation snapshot` / `fund snapshot` 支持 `--thscodes` 逗号批量，能用批量就用批量。
- `data sync` 是**下载+导入**（实测 148s），无法并行压缩；正确做法是**后台启动它**，同时并行跑 API 取数，最后再导出 parquet（导出前本地库必须已同步完）。
- 并行时**不要**把输出接管道（见 `ths_cli` 模块头部铁律）。

**板块池扩到 90 个后的日更真实成本（2026-09-24 实测）**：单日 `daily_prep` 的「行情/基础组」共 **99 个调用**（90 个二级行业历史 + 上证 + 7 只 ETF + 4 个指数），`workers=8` 用时 **66.6s**；整条链路（含 `data sync` ≈150s 与取数并行、parquet 导出、形态扫描、轮动、交叉）**总耗时 225.4s**。→ 结论：**90 个板块的取数成本可接受（约 +40s/日）**，不要为了省这点时间把板块池缩回去（覆盖率会掉到 27.5%，见坑 71）。

## 69. `special`（特色数据）接口并发上限与超时（2026-09-21 实测，并行取数的例外）

坑 68 说「独立调用一律并行」，但**`special` 特色数据接口是例外**：

| 接口 | 并发上限 | 单次超时 | 说明 |
|---|---|---|---|
| `index history` / `index snapshot` / `valuation snapshot` / `fund snapshot` | workers=8 稳定 | 90~120s | 行情/基础类，可放心并行 |
| `special limit-up-pool` / `limit-down-pool` / `limit-break-pool` / `dragon-tiger` | **workers ≤ 3** | **≥180s** | 并发高会被上游限流 |

**实测现象**：把 5 个 special 调用与 27 条指数历史放进**同一个 workers=8 的批次**里跑 →
`limit-break-pool` / `limit-down-pool` / `dragon-tiger(org)` 全部返回
`{"ok":false,"error":{"code":"FUYAO_5002","category":"upstream","message":"... timeout"}}`，
`special dragon-tiger`（整张龙虎榜）还直接 `TIMEOUT >90s`。

**后果（隐蔽）**：这 3 个池失败后文件仍是 `{"ok": false}`，若下游不检查 ok 就会算出**错数** ——
当天实测「封板率 100%」，正是炸板池取不到导致（`封板率 = 涨停 ÷ (涨停 + 炸板)`，炸板为 0 则恒为 100%）。

**正确做法**：
1. `special` 组**单独一批**，`workers=min(3, n)`、`timeout=180`、`retries=2, backoff=3`；
   行情/基础类另起一批 `workers=8`。
2. **落盘后必须校验 `ok`**：失败项要重取或**在报告里显式标注缺失**，绝不能拿空数据继续算派生指标。
   `daily_prep.py` 的做法：炸板池为空时**不计算封板率**，直接打印「炸板池数据缺失 → 不计算」。
    **⚠️ 重试要设上限，否则把 40s 的失败放大成十分钟级**：同一批 `special` 调用在 00:45 复测时，
    `limit-up-pool` 已从 1.3s 变成 **13.7s**、`limit-down-pool` **43.4s 后失败**、`limit-break-pool` **46.1s 后失败**、
    `dragon-tiger` 直接超时 —— 即该组接口在**被高频调用后 / 夜间**会进入降级状态。
    若按 `timeout=180 + retries=2` 跑，单次失败最坏要 180×3+9 ≈ 9 分钟，整条链路就被拖死（当日实测卡了 3 分半仍未过第一步）。

    **因此 `daily_prep.py` 的策略是**：
    1. **同目标日的有效文件直接复用**（`{"ok": true}` 才复用；当天反复跑不会重复拉同一批数据），`--force-refetch` 可强制重取；
    2. `special` 组 `workers=min(3,n)`、`timeout=90`、**`retries=1`**（不放大）；
    3. 失败后**明确列出未取到的文件**并给出补数命令：`python daily_prep.py --date <日> --only-special`
       （上游恢复后只补这批，不动其他数据）；
    4. 缺失相关派生指标一律**不计算、报告里标注缺失**（见上一条的「封板率 100%」）。

## 70. `index snapshot` 返回**实时行情**，不能用来取历史某日的收盘（2026-09-23 实测）

**现象**：2026-09-23（周三）中午为 09-22 出报告，`daily_prep` 用 `index snapshot --thscodes ...` 取的指数行是
`上证 3938.08 −0.36% / 深证 −0.58% / 创业板 −0.43% / 沪深300 −0.50%` —— 但 09-22 **真实收盘**是
`上证 3952.13 +0.06% / 深证 13723.74 −0.05% / 创业板 3399.93 +0.01% / 沪深300 4544.59 +0.11%`。

**原因**：`index snapshot` 是**实时报价**接口，它返回「当前价 + 相对上一收盘的涨跌」。
在 09-23 中午调用，给出的就是 **09-23 的盘中价**（3938.08）与相对 09-22 收盘的跌幅（−0.36%）。
即：**同一个数字 3938.08 是"今天"，3952.13 才是"目标日"** —— 两者相差一个交易日，报告会整体写错。

**判据（怎么一眼看出踩了）**：snapshot 的 `last_price × (1 + pct)` 反推出的「昨收」应当等于**目标日的前一日**收盘；
若反推值等于**目标日**收盘，说明 snapshot 已跳到下一天。

**正确做法**：历史日期的指数收盘一律用 `index history --end-ms <目标日>`，取最后两根 bar 自己算涨跌
（`daily_prep` 已改为这样，并落盘 `idx_close_MMDD.json`）。
**同类风险**：`valuation snapshot` / `fund snapshot` 也是"最新快照"语义 —— 它们给的是**当下**的 PE/PB/净值，
用于历史日期会混入当日盘中数据；需要严格对齐某日时，应优先用**历史/财报口径**接口（`financials *`、`fund history`）。

**当日 vs 历史的分工**：
| 用途 | 接口 | 说明 |
|---|---|---|
| 当天收盘后出当天报告 | `index snapshot` 可用（但 history 同样可靠，且更一致） | 两者一致 |
| 出**历史某日**报告 | **必须用 `index history`** | snapshot 会给"今天" |

   覆盖补齐后（对照 `has_board` 组与基线完全一致，可证明覆盖已达 100%），增益归零（均值略降、中位略升、胜率略降 → 落在噪声内）。
2. 用户主观上「板块不行的不看好、宁可少给」的偏好**仍可实现**（它改善**中位数** −0.758→−0.669 与尾部观感），
   但报告与文档**必须写明这是偏好而非已验证优势**，不得再声称"板块过滤提高收益"。
3. **真正有证据的是「涨停配额」（v1.3）**：R1（涨停优先）T+5 −0.059%/胜率 44.1% → R2（涨停≤2）+0.368%/46.6%；
   该对比两边都用**全量候选池**、与板块覆盖率无关。

**方法论教训**：做「规则级回测」时**必须把"数据可得性造成的样本收缩"单独设成对照组**（本次即 `has_board`）——
否则容易把「样本变小/变优质」的效应误判为「规则本身有效」。这次就踩了这个坑并在下一轮自我推翻。

**实现规范**：
- 读缓存 JSON 的 `try/except` **不要静默返回空**（本次曾漏 `import json` → `NameError` 被 `except` 吞掉 → 回测跑出"0 个样本"的假结论却不报错）。
- **缓存要与板块池一致**：`sector_map.members()` 已加校验（缓存板块集合 ≠ 当前池则自动重建），
  否则板块池扩容后旧缓存会让过滤逻辑**静默退化**回 27.5% 覆盖。

## 74. `index history` / `fund history` 的「5 年窗口」是硬限制，且超限时**静默返回空**（2026-09-30 实测）

**现象**：`ok=true`、无 `error`，但 `data.item` 是**空数组**（`count=0`）。不会报错，极易被当成"该指数没有数据"。

**实测（000300.SH，结束日固定 2026-09-30）**：

| 起止 | count |
|---|---|
| 2021-09-30 ~ 2026-09-30（正好 5 年） | **1212 ✅** |
| 2021-07-01 ~ 2026-09-30（5.2 年） | 0 ❌ |
| 2020-09-30 ~ 2026-09-30（6 年） | 0 ❌ |
| 2020-01-01 ~ 2021-12-31（结束日在过去） | 0 ❌ |

**两条规则（缺一不可）**：
1. **窗口跨度 ≤ 5 年**（超过即空，差 2 个月也不行——按自然日算，不是按交易日）。
   ⚠️ **贴边也返回空**（2026-09-30 补充实测）：`2026-09-28` 往前推 **1826 天**（正好 5.0 年）→ `count=0`；
   同样 5 年但起点为 `2021-09-30`、终点为 `2026-09-30` → `count=1212` ✅。
   即**边界不是"≤5 年"，而是"明显小于 5 年"**。稳妥做法：**留 40 天边距**
   （`span = min(int(years*365.25), int(5*365.25) - 40)`，见 `value_evidence.SAFE_MARGIN_DAYS`），
   并**从返回数据里读真实起止日**，不要用请求参数当区间。
2. **`--end-ms` 必须落在近期**（≈ 今天）；**任何"结束日在过去"的区间一律返回空**，
   即**无法用这个接口取历史某一段**，只能取"截止今天的近 N 年"。

**推论（做长历史分析时的唯一出路）**：
- 需要 **>5 年** 或 **任意历史区间** 的指数/基金序列 → **本地 DuckDB**（`v_daily_qfq` / `v_daily_hfq`，
  日 K 自 2016-08 起）自建；但本地库**只有个股与 ETF 的日线口径**，没有官方指数成分权重，
  因此**算不出市值加权指数**（见坑 75）。
- 代码里必须**显式校验 `count`**，不能只看 `ok`。`value_evidence.py` 的 `load_index()` 用
  `len(p2) < 200 → 报「样本不足」` 兜住这一点，是可复用写法。

## 76. 「找不到 CLI」的真因：node 版本目录更换 → npm 全局包一起消失（2026-10-04，已发生 2~3 次）

**症状**：脚本报「找不到 hithink-finance CLI」或 `command not found`。

**❌ 错误的第一反应**：以为「环境变量 / PATH 配错」。
**实测 PATH 与 `npm config get prefix` 都是对的**，改环境变量通常**没用**
（本项目 2026-09-02 就因误判触发过一次无谓重装）。

**✅ 真因**：WorkBuddy 用「**每个 node 版本一个目录 + 版本指针文件**」管理 node：
- `~/.workbuddy/binaries/node/versions/<版本>/` —— 每个版本一个目录
- `~/.workbuddy/binaries/node/versions/current` —— **纯文本文件**，内容是版本号（如 `22.22.2-6`）
- **npm 全局包装在 `versions/<版本>/node_modules` 内**（版本专属目录）

→ **版本一升级**：新建新版本目录 + 更新指针 + 更新 PATH，**旧版本目录被删除 → 全局包全丢**。
而 PATH / npm prefix 都指向那个**新的空目录**，所以「看着完全正常」。
**旁证**：PATH 里长期残留**已不存在**的旧版本目录（如 `22.22.2-2`）。

**修复（三层，已落地）**：
1. **代码层（主要手段）**：`ths_cli.cli_command()` 与 `review_picks._cli_cmd()` 的解析顺序加入
   **版本无关目录** `<node根>/cli-shared/node_modules`、`/workspace/node_modules`；
   并在 PATH 无 node 时用 `versions/current` 指针解析 `node.exe`
   → **脚本不再依赖 PATH 正确**。
2. **安装层**：CLI 装到**版本无关**的 `~/.workbuddy/binaries/node/cli-shared/`，
   配稳定启动器 `cli-shared/hithink-finance.cmd`（node 运行时从 `versions/current` 动态解析）。
3. **镜像层**：`~/.npmrc` 固定 `registry=https://registry.npmmirror.com`。
   ⚠️ **官方源 `registry.npmjs.org` TCP 可达但会卡死**：实测 `npm i -g` 跑 **5 分钟零输出零写盘**；
   换镜像 **31 秒装完**。**本机 npm 装包一律用镜像。**

**排查顺序（照做，不要猜）**：
① `<cli> --version` **实测** → ② `npm root -g` → ③ 看 `<prefix>/node_modules` 里有没有包
→ ④ 没有就用**镜像**重装（装到 `cli-shared`）。

**⚠️ 两个沙箱约束**：
- `setx` / `reg.exe` 在本机被 **Program Blacklist 拦截** → **无法用命令设用户级环境变量**。
  所以**不要依赖 `HITHINK_CLI`**，靠上面的代码层解析才可靠（用户若要设，需手动在「系统属性 → 环境变量」填）。
- `.cmd` 批处理**必须 CRLF 行尾**：LF-only 会被 `cmd.exe` 解析异常 —— 实测一个 LF 版 shim
  **直接挂死**（连 `echo` 都不输出、进程被 SIGTERM）；且**内容保持纯 ASCII**（中文注释在 GBK 控制台可能乱码）。

**现象**：`check_build --script gen_rotation_MMDD.py` 报两条**误报** ——
`S5  DATE 与模板默认值相同（2026-08-21）`、`N1 疑似手抄的当日市场数字`（可同日 `lu_MMDD.json` 明明在场）。

**真因（结构性，不是 bug）**：`render_rotation_report.py` / `render_sentiment_report.py` 走的是
**双锚点替换数据区** —— 注入区间是 `# ==== 数据 ====` 与 `# ==== 渲染 ====` 两个标记**之间**。
而**模板自己的示例 `DATE = "2026-08-21"` 落在数据标记之前、不在替换范围内** →
生成脚本里出现**两个** DATE：

    DATE = "2026-08-21"                    # ← 模板残留（死代码，不生效）
    # ================= 数据 =================
    DATE = "2026-10-13"                    # ← 注入的（生效）

⚠️ **`render_picks_report.py` 不受影响**：它的替换起点**就是**模板第一个 `DATE = "`，所以只有一个 DATE。
→ 这也解释了「为什么只有轮动/情绪会天天报这两条」。

**必须遵守的口径**：
1. **判定脚本日期一律取最后一个 `DATE` 赋值**（= 生效值）。取第一个会拿到模板示例日期：
   `S5` 误报「与模板默认值相同」；`N1` 拿 `0821` 去找 `lu_0821.json`（不存在）→ 豁免失效 → 误报「手抄」。
2. **不要"顺手清理"残留的那个 DATE**：它无害；但若误把它当定义、或反过来只留第一个，行为就错了。
   **凡是从生成脚本反读配置（日期 / 池大小 / 阈值）的地方，都要先问「我读的是模板示例还是注入值」。**
3. **平台侧同样适用**：平台的 `splicer.py` 也是双锚点替换 → 生成脚本同样有两个 DATE，
   见 `构建个人量化平台指南.md §4.6`。

**已代码化**：`check_build` 的 `_pipeline_sourced()` 与 `check_script._const()` 均改为取**最后一个** DATE，
`--selftest` 含负例自证（双 DATE 不误报 / 用生效日期溯源 / **生效值仍等于模板默认值时仍须告警**）。
