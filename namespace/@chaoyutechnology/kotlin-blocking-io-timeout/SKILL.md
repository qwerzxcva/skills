# Kotlin 协程阻塞 IO 超时修复

## 这个技能是干嘛的？

解决 Kotlin 协程里一个经典坑：`withTimeout` 和 `job.cancel()` 取消不了阻塞式原生 IO。如果你的 Android 播放器、网络请求或文件读取会莫名其妙卡死，加载弹窗永远转圈，这个技能给你一套经过实战验证的修复思路和代码模板。

## 你会拿到什么？

- 一套清晰的修复思路：为什么 `withTimeout` 会失效、真正有效的打断方式是什么。
- 一段可直接参考的 Kotlin 代码模板：把阻塞 IO 放进独立线程 + Future 超时 + 强制关闭底层资源。
- 一份自检清单：帮你排查项目里是否踩了同样的坑。

## 这个问题长什么样？

- 协程里包了阻塞式原生 IO：Socket 读、文件读、JDBC、Process、Samba 文件读等。
- 用 `withTimeout(5000) { input.read(...) }` 想 5 秒超时。
- 结果远端不回数据时，`read()` 永远阻塞，`withTimeout` 只设了一个取消标志，线程卡在 native 里到不了挂起点。
- 用户看到的表象：加载弹窗一直转、界面卡死、协程永远不回来。

## 修复思路（大白话版）

1. 把阻塞 IO 放到一个独立的单线程线程池里跑，别占着协程调度线程。
2. 用 `Future.get(timeout)` 等结果，超时了就强制关闭底层的 socket 或连接。
3. 底层资源一关，阻塞的 `read()` 立刻抛异常退出，线程就能回收了。
4. 整条调用链都包在这个 Future 里，避免嵌套提交导致死锁。
5. 取消按钮也是同理：取消协程的同时，强制关闭底层资源，这次取消才真正生效。

## 生成的代码模板可以用在哪里？

- Android 播放器里网络取流、文件下载、Samba 读取等会卡住的场景。
- 任何用 Kotlin 协程包阻塞 IO 的地方：Retrofit/Okio 底层 socket、JDBC 查询、Process 调用等。
- 需要给「加载中」对话框一个真正可靠超时的项目。

**Q：为什么 `Dispatchers.IO` 不能解决问题？**  
A：`Dispatchers.IO` 只是让阻塞 IO 不卡主线程，但 `withTimeout` 依然无法打断 native 里的 `read()`。关键还是要从外部强制关闭底层资源。

**Q：用了这个套路就能彻底避免卡死吗？**  
A：能避免「协程永远挂起」这一类卡死。但如果你的网络层本身设计有问题，还需要结合具体代码一起看。
