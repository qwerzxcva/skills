# 回收与软删治理设计方案（纯中文说明）

> 目标：让"被删除 / 被冷处理的记忆"不会永久堆积在磁盘上，同时守住"误删可救"的安全网。
> 适用范围：本地记忆系统（agent-local-memory-keeper）这一套技能。
> 本文所有功能均用中文说明，不出现英文命令或符号。

## 一、先回答你的核心问题：归档是不是软删除？

**是。归档就是教科书式的软删除。**

归档这个功能的作用是：把一条记忆从"活跃区"物理搬到"归档区"文件夹，并给它贴上"已归档"的标记。它的设计意图是"冷处理"——让这条记忆默认不再出现在日常搜索结果里，但：

- 文件本身**不销毁**，只是沉到冷层；
- 你随时可以把它**移回活跃区**（反归档）；
- 默认搜索看不到它，但**深度搜索仍能把它召回来**。

所以归档的本质是：逻辑上消失、物理上永驻。这正是你担心的"被删除的文件永久地呈现在那里"的根源。

## 二、这套系统里，所有"删了但没真消失"的地方（逐一说明作用）

除了归档，系统里还散落着好几处"看起来删了、其实还在"的机制。下面每个都用中文说清它"是干什么的、为什么还在"：

1. **归档区（已归档状态）**
   作用：把不常用的记忆冷处理，减轻日常召回噪音。文件已搬走、打了"已归档"标记，默认搜索不可见，但深度搜索可找回、可反归档。**物理仍在。**

2. **被取代记忆（已取代状态）**
   作用：当你用一条新记忆去纠正一条旧记忆时，旧的那条会被标成"已取代"，新记忆记着"我取代了谁"。目的是保留来龙去脉（血缘），方便追溯你观点怎么变的。默认召回隐藏已取代的旧记忆，但文件**物理仍在**，只是留作历史。

3. **隔离候审区（敏感待决议）**
   作用：当一条记忆疑似含有密钥、密码等敏感信息时，系统不让人直接看，而是把它丢进"隔离候审区"，等你人工决定：放行、删除、还是保留。在被决议之前，它**物理仍在**，只是默认不可见。

4. **暂存与自动来源（默认隐藏）**
   作用：系统平时被动"偷听"对话自动攒下的记忆，默认不进正式召回（怕噪音太大），需要你显式要求才纳入。这类记忆**物理仍在**，只是默认藏起来。

5. **新鲜度过滤（按时间隐藏，不真删）**
   作用：日常召回时会按"距今多久"或"截止日"把太老的记忆过滤掉，让结果更聚焦。注意它只是**过滤显示**，并不删除文件——老记忆**物理仍在**。

6. **版本快照与手工备份（覆盖留痕）**
   作用：当你覆盖更新一条记忆时，系统会自动留一份旧版快照；某些配置文件也会留备份。目的是"改错了能回退"。这些都是**物理仍在**的历史副本。

7. **衰减降权（降分沉底，仍可见）**
   作用：长期没人复述的记忆会慢慢降低重要度分数，沉到结果底部。它**不算删除**，文件仍在、仍能搜到，只是排得靠后。

**结论：真正会"永久堆积"的是前四项（归档、被取代、隔离候审、残留快照与备份）。** 它们都物理存在、永不自清。

## 三、最关键的现状发现：你想要的"180天自动清理"原本是坏的（已修复）

你设想的"归档后沉淀180天自动删除"，这套系统在文档里**声称有**，但代码层面**曾是失效的**（已修复，彻底改为「自动归档 + IMA 镜像」，绝不删除）：

- 文档宣传了一个"彻底清理遗忘记忆"的功能，设计是：找出"已归档 + 低重要 + 超180天"的记忆，默认只出一份待删清单、不动真文件（很安全）。
- 早期版本这个功能内部调用了一个**根本不存在的底层函数**——曾实跑验证过：代码里只有两个孤零零的相关常量，那个被调用的函数名压根没实现。结果就是：这个清理功能一运行就报错。

**修复与重新决策**：经用户拍板，原"自动删除"方案被**彻底改为「自动归档 + IMA 镜像」**——软删记忆本地沉到 `archive/` 且永远保留，同时推到 IMA 知识库（带【归档】标记）作为跨设备/换机的可检索冷存储。「将来遇到了还能找到」。代码层面 `archive_sweep`（原 `reclaim`）已实现：时间沉淀 + 容量配额 + 保护规则 + 两次运行冷却，但**终态从 `delete` 改为 `archive`，绝不硬删任何记忆**。这同时守住了「安全网优先」与「软删不堆积（靠 IMA 冷存储兜底）」两条原则。

> 结论：软删文件本地仍会保留（设计如此，便于 `recall --deep` 找回），但**再也不会被自动销毁**；跨设备的"不遗忘"由 IMA 镜像承担。每周自动化的 `archive --review` 会复查归档项是否过时 / 有更优方法替代。

## 四、设计上必须调和的一对矛盾

从这套系统自身的设计记忆里，能提炼出一条很"贵"的经验：

> **安全网优先**：真正的删除不可逆、默认拒绝；遗忘走"归档（可救）+ 默认演练（只出报告不真删）"；自动化流程明确禁止自动硬删。这是防误删的命门。

而你现在要的是**反方向保证**：软删文件不能永久堆积。

两者的冲突点在于——"自动真删"会戳破安全网。所以统一方案必须同时满足：

- 误删仍可救（核心层、高重要、未过期的记忆永不自动删）；
- 软删文件有上限、最终会被清掉。

我倾向用"**两次确认 + 重要度地板 + 容量配额**"来调和，而不是直接无脑定时删。

## 五、统一设计方案：回收治理框架

把散落的软删清理**归一**成一个统一的"回收"功能，替换掉那个坏的"彻底清理"功能。

**1. 给所有软删状态打"沉淀起始时间"**
归档时、被取代时、隔离候审被决议时，各记一次时间戳。这是"180天"的计时起点。

**2. 两种回收模式（对应你说的两句话）**

| 模式 | 触发条件 | 对应你的原话 | 推荐度 |
|---|---|---|---|
| **时间沉淀** | 沉淀满180天 **且** 重要度低于阈值 | "180天后自动删除" | 主模式 |
| **容量回收** | 软删总量超过设定配额，最老的先清（环形覆盖） | "180天的文件被后续软删覆盖掉" | 兜底上限 |

**3. 保护规则（守住安全网）**
- 绝不碰"活跃"记忆，只动归档、已取代、已决议的隔离候审这三类。
- 属于核心层、重要度达到阈值以上、带未过期截止日、或正被别的记忆引用为来源的——一律豁免。
- 每次运行清理数量封顶（比如最多50条），防止一次清太多。

**4. 安全闸（沿用系统自家经验）**
- 默认只出"待清理清单"报告，不动真文件；
- 自动化流水线里只跑"只读报告"，把候选清单并入每周评审；
- 真正执行删除必须**人工确认**，且要求该条目**至少在前一次报告里出现过**（两次运行冷却，防手滑误删）。

**5. 接入点**
- 在每周自动化流水线的末尾，追加一步"只读回收报告"；
- 真正的删除动作留在每周人工评审时由人批准。

## 六、需要你拍板的三个决策（中文表述）

**决策一 · 默认开还是关？**
- 甲（推荐）：默认关闭 / 仅出报告。保持系统"安全优先"的基因，你手动开启真删。好处：零误删风险。代价：不主动清。
- 乙：默认"时间沉淀"模式、自动出报告但不删。好处：你能持续看见堆积。代价：还是要人批才删。
- 丙：默认"时间沉淀"模式、自动真删。⚠️ 不推荐——直接戳破安全网，与系统核心原则冲突。

**决策二 · 时间模式和容量模式要不要同时开？**
- 推荐**两个都做**：时间为主、容量为兜底。只开时间的话，少量软删永远碰不到180天阈值、仍会缓慢堆积；容量模式才真正封顶。

**决策三 · 先做哪一步？**
- 强烈建议**先修那个坏的"彻底清理"功能**（实跑修通 + 补一条声明校验），再在它之上长出"回收"统一框架。否则新方案还会踩同一个"文档虚标"的坑。

## 七、建议的落地顺序

1. 修通坏的清理功能，补声明校验（堵当前虚标）。
2. 加"沉淀时间戳"字段。
3. 实现"回收"统一功能（时间模式 + 容量模式 + 保护规则 + 安全闸）。
4. 接入每周只读报告。
5. 文档同步、发版。
