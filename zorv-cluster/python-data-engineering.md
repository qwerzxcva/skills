# Python 数据工程规程

## 一、处理引擎选型（先选再写）

| 场景 | 选择 |
|---|---|
| 单机 < 2GB 数据、需丰富生态 | pandas |
| 单机大数据、要并行与惰性求值 | polars |
| 亿行级、需 SQL 与列存、可持久化 | duckdb（首选，配 parquet） |
| 需要断点续算的大矩阵 | duckdb 逐批 INSERT + CHECKPOINT |

**不要用 pandas 硬扛亿行**：先估内存（行 × 列 × 8 字节 × 2~3 倍膨胀），超一半可用内存就换引擎或分块。

## 二、内存控制（最常翻车）

- 大矩阵写入必须**逐批 INSERT + CHECKPOINT**；一次性 `concat` 全量写入会被 OOM killer 杀。
- 逐票/逐批读取，单批行数宁小勿大；用 `chunksize` 或 `iter_batches()`。
- 及时 `del` + `gc.collect()`；避免在循环里不断 append DataFrame。
- 用 dtype 收窄（int32/float32、category）能省 30~60% 内存。

## 三、增量与断点（必须可续跑）

- 每个长任务写**进度标记文件**（如 `_done_xxx.txt`，记录 已完成/总数），中断后从标记续跑。
- 任务结束写 `_done_xxx.txt` 后，才允许下游消费（防止半成品进管道）。
- 幂等：同一批数据重复跑不得产生重复行（主键 upsert 或先删后插）。
- 断点续算的大矩阵：记录已处理的票/日期区间，重跑时跳过。

## 四、CLI 工程化

- 入口用 `argparse`（或 typer），参数显式：日期区间、票池、并发度、dry-run。
- 日志：`logging` 分级 + 时间戳，进度用逐 N 条打印（不要每行 print）。
- 重试：网络请求带指数退避 + 超时；失败票据落盘为 `_failed.txt` 而非直接丢弃。
- 必须支持 `--dry-run`：只校验不写库。

## 五、密钥与安全（血的教训）

- **token/密钥绝不写入 heredoc、日志、异常堆栈**：运行时会替换成掩码串，导致静默失败。
- 正确做法：token 从环境变量读取，敏感操作写脚本文件再执行。
- 校验 token 完整性用 `grep -o 'ghp_[A-Za-z0-9]\{30,\}'` 排除掩码串。
- 推送固定顺序 `put(repo, tok, path, local)`，参数顺序错会推到错仓库。

## 六、GitHub Actions 编排

- 定时任务用 `schedule.cron`（UTC），长任务加 `timeout-minutes` 与 `concurrency` 防重叠。
- 大产物不要进 git 历史：用 release asset 或独立分片仓库。
- 失败要能在 Actions 日志里看出是哪一步、哪只票、什么错误。
- 断点续跑在 CI 里靠外部存储（仓库里的 `_done_*` 或 artifact），不靠本地状态。

## 七、交付自检清单

- [ ] 脚本可重入、幂等（重复跑结果一致）
- [ ] 有进度输出与断点文件
- [ ] 大数据走逐批写入，未一次性 concat
- [ ] 失败票据落盘，可重试
- [ ] 无明文密钥，日志已检查
- [ ] 有 `--dry-run` 与运行说明（命令、参数、预期产物）
- [ ] 输出数据附行数/票数/日期范围校验
