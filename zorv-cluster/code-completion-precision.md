# 代码补全精准度规程

## 一、上下文包（缺一项就容易补错）

补全前必须掌握：
1. **光标前** 40~60 行（含当前函数签名、已用变量）
2. **光标后** 10~20 行（判断后续调用方期望的返回形态）
3. **当前作用域符号**：已 import 的类型/函数、类字段、可见的局部变量
4. **类型定义**：被调用方/入参类型的真实定义，不是猜的
5. **项目规范**：命名风格、错误处理方式、日志方式、分层约束

缺第 3、4 项时，**先检索真实定义再补**，不允许凭印象写 API。

## 二、反幻觉（最高优先级）

- 只使用**确实存在**的符号。不确定的 API：先检索代码库/文档确认，确认不了就换成自己写的实现，并说明"未确认该 API 存在"。
- 不许编造：库函数名、参数顺序、配置项键名、注解属性。
- 不许引入新依赖来完成补全；确有必要时，停下来单独说明理由与替代方案。
- 不臆造"看起来合理"的错误类型/返回类型；返回类型以调用方使用方式 + 现有声明为准。

## 三、补全顺序（自顶向下，一层一验证）

1. 签名与类型：先确定输入输出契约（含可空性、错误类型）。
2. 骨架：分支与早返回先落地（guard clause），再填细节。
3. 实现：每写一个调用就核对参数与返回值。
4. 边界：空集合、null、异常路径、并发、超时。
5. 测试：至少一个正常路径 + 一个边界路径。

## 四、风格对齐

- 命名：跟随同文件既有风格（`getX` vs `x()`、snake_case vs camelCase）。
- 错误处理：跟随项目既有范式（Rust `?` + thiserror / Kotlin `Result` / Java 异常 / Go `error` 返回），不要混入新范式。
- 日志：用项目已有的 logger 与级别，不引入 print/println。
- 注释：只写"为什么"，不写"是什么"；不写与代码矛盾的注释。
- 格式化：缩进、行宽、import 排序跟随项目。

## 五、交付形式

- 默认**只给改动片段**，并标明插入位置（文件 + 锚点）；不要整文件覆盖，除非用户要求。
- 多处改动按文件分组，逐块给出。
- 有不确定点时在片段后用一行标注 `// 待确认：xxx`，而不是假装确定。

## 六、精度自检清单

- [ ] 所有调用的符号在项目中真实存在（或已说明是自写）
- [ ] 类型/可空性与现有声明一致
- [ ] 没有多余或缺失的 import
- [ ] 没有未使用的变量
- [ ] 边界条件已处理（空、null、异常、超时）
- [ ] 与项目错误处理/日志/命名范式一致
- [ ] 可直接编译，无需二次修补
- [ ] 不确定处已显式标注，没有隐藏猜测
